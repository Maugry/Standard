**Статус:** Действующий
**Дата:** Февраль 2026
**Лицензия:** Открытый стандарт (Реализация: MIT)

## 1. Обзор

Стандарт Umka Kiosk определяет универсальный протокол для музейных мультимедийных киосковых систем. Стандарт охватывает:

- Режимы работы и их конфигурации
- Протокол управления в реальном времени (MQTT)
- Синхронизацию контента (REST API)
- Архитектуру локального хранения контента (local-first)
- Интеграцию с планшетами экскурсоводов и IoT-устройствами

### 1.1 Принципы проектирования

1. **Local-first** — Киоски всегда работают с локально сохранённым контентом. Подключение к серверу используется для синхронизации и удалённого управления, а не для основной работы
2. **CMS-агностичность** — Стандарт определяет API-контракт между киоском и сервером. Серверная реализация CMS не предписывается
3. **Аппаратная агностичность** — Плеер работает на ПК с Windows и поддерживает различные устройства вывода: мониторы, телевизоры, сенсорные экраны, LED-панели, проекторы и аудиосистемы
4. **Основан на стандартах** — Любая реализация, соответствующая этой спецификации, является Umka-совместимой. Реализации будут разделять код протокола по замыслу

### 1.2 Терминология

| Термин | Определение |
|--------|-------------|
| **Umka** | Система управления музейными киосками: сервер (CMS), административный интерфейс и приложение для планшета экскурсовода |
| **Киосковое ПО** | Универсальное мультимедийное ПО для киосков (Umka Player), построенное на Electron |
| **Режим Loop** | Режим работы киоска с автоматическим циклическим воспроизведением медиаплейлиста (видеоплеер) |
| **Режим Browse** | Интерактивный режим работы киоска с меню/каталогом для самостоятельного выбора контента посетителями (витрина) |
| **Режим Custom** | Режим работы киоска с нестандартной функциональностью (например, интерактивная игра) |
| **Скринсейвер** | Визуальное отображение состояния ожидания |
| **Контент-пакет** | Набор контента (медиафайлы, настройки), назначенный конкретному киоску |
| **IoT-устройство** | Физическое устройство (кнопка, датчик), подключённое к системе через Umka API |
| **Физический триггер** | Аппаратная кнопка, отправляющая событие в систему для запуска контента на киоске |
| **Планшет экскурсовода** | Планшетное приложение для управления воспроизведением на киосках во время экскурсий |

## 2. Режимы работы

Umka определяет три стандартных режима работы. Каждый режим может быть настроен для различных аппаратных конфигураций и сценариев использования.

### 2.1 Режим Loop

Автоматическое циклическое воспроизведение медиаплейлиста (видео, изображения, аудио). Порядок плейлиста и длительность показа изображений настраиваются в CMS.

**Общее поведение:**
- Воспроизведение контента из упорядоченного плейлиста
- Возврат к началу после последнего элемента
- Удалённое управление через планшет экскурсовода (MQTT)
- Контент синхронизируется с сервера, воспроизводится из локального хранилища

#### Конфигурация: Непрерывная (без тач)

**Сценарий использования:** LED-панели, видеостены, неинтерактивные дисплеи

```
Playlist[0] → Playlist[1] → ... → Playlist[n] → (цикл)
```

- Автоматическое воспроизведение в бесконечном цикле
- Видео, изображения и аудио в плейлисте
- Автоматические переходы между элементами плейлиста
- Нет взаимодействия пользователя с устройством

#### Конфигурация: Интерактивная (Тач + Скринсейвер)

**Сценарий использования:** Сенсорные киоски с воспроизведением видео

```
Скринсейвер → (нажатие «Начать») → Плейлист → (конец/ожидание) → Скринсейвер
```

- Скринсейвер отображается в состоянии ожидания
- Кнопка «Начать» на скринсейвере для запуска воспроизведения
- Кнопка «Назад» во время воспроизведения для возврата к скринсейверу
- Возврат к скринсейверу после завершения воспроизведения
- Управление видео: воспроизведение/пауза, перемотка, громкость
- Элементы управления появляются при касании, скрываются после таймаута бездействия
- Настраиваемый таймаут бездействия для возврата к скринсейверу

#### Конфигурация: По триггеру (IoT-кнопка)

**Сценарий использования:** Экспонаты с физическими кнопками рядом с дисплеями

```
Скринсейвер (без кнопки «Начать») → (IoT-сигнал) → Плейлист → (конец) → Скринсейвер
```

- Ожидание сигнала от физической кнопки (IoT-устройства)
- Запуск воспроизведения по получению события триггера через MQTT
- Возврат в состояние ожидания после завершения воспроизведения
- Сенсорное взаимодействие на киоске не требуется

#### Конфигурация: Только аудио

**Сценарий использования:** Фоновая музыка в залах музея

```
Ожидание (тишина) → (команда) → Аудио-плейлист → (цикл)
```

- Нет видеовыхода (дисплей не требуется)
- Воспроизведение аудиофайлов (MP3, WAV) через динамики
- Каждый зал — отдельный «киоск» в аудиоконфигурации
- Управление: громкость, выбор трека, воспроизведение/пауза через планшет экскурсовода

#### Конфигурация: Проектор (Пассивный дисплей)

**Сценарий использования:** Короткофокусные проекторы, проекционный мэппинг

```
Чёрный экран → (триггер/команда) → Плейлист → (конец) → Чёрный экран
```

- Полностью пассивный (нет экранных элементов управления)
- Запускается командой MQTT, планшетом экскурсовода или IoT-устройством
- Может воспроизвести один раз и вернуться к чёрному экрану, или зациклиться
- Может отображать статическое изображение вместо чёрного экрана в состоянии ожидания
- Нет сенсорного взаимодействия

### 2.2 Режим Browse

Интерактивный режим с меню/каталогом для самостоятельного выбора контента посетителями.

**Общее поведение:**
- Иерархическая навигация по меню с неограниченной глубиной вложенности
- Множество типов контента (видео, статьи, галереи изображений)
- Интерфейс, оптимизированный для сенсорного ввода
- Возврат к скринсейверу по таймауту бездействия
- Удалённое управление через планшет экскурсовода (MQTT)

#### Витрина контента (Каталог)

- Отображение объектов в виде сетки карточек с изображениями и заголовками
- Прокручиваемая витрина (вертикальная или горизонтальная в зависимости от ориентации экрана)
- Нажатие на карточку для просмотра подробного контента
- Сетка адаптируется к ориентации и разрешению экрана

#### Детальный просмотр объекта

- Заголовок и описание объекта
- Список медиа: фотографии, видео
- Навигация по медиаэлементам (прокрутка, свайп или карусель — зависит от реализации)
- Подпись и описание для каждого медиаэлемента (при наличии)
- Полноэкранный просмотр медиа
- Воспроизведение видео с элементами управления

#### Система скринсейвера

- Привлекающий внимание контент в состоянии ожидания
- Карусель изображений и/или видео с автоматической ротацией
- Настраиваемый текст заголовка и подзаголовка
- Опциональная кнопка «Начать» с настраиваемым текстом
- Настраиваемая длительность таймаута бездействия

---

### 2.3 Режим Custom

Нестандартная функциональность киоска. Приложения в режиме Custom реализуют собственный интерфейс и логику, но интегрируются с системой Umka для мониторинга и управления питанием.

**Сценарий использования:** Интерактивные игры, кастомные интерактивные инсталляции

**Обязательная интеграция с Umka:**
- Публикация heartbeat (каждые 10 секунд)
- Команды управления питанием (выключение, перезагрузка)
- Отчёт о статусе (online/offline)

**Опциональная интеграция:**
- Синхронизация контента
- Управление с планшета экскурсовода
- Таймаут бездействия и авто-сброс

**Специфичные требования для игр (при необходимости):**
- Интерфейс, оптимизированный для сенсорного ввода
- Возврат в начальное состояние при бездействии (настраиваемый таймаут)
- Игровая механика и сценарий определяются для каждой реализации

## 3. Функциональные требования

### 3.1 Общие (все режимы)

- Отображение логотипа музея (настраивается в CMS)
- Настраиваемый таймаут бездействия перед возвратом в состояние ожидания
- Автоматический сброс в состояние по умолчанию при бездействии пользователя
- Плавные переходы между элементами плейлиста (режим Loop)
- Адаптивная вёрстка для различных разрешений и ориентаций экрана

### 3.2 Режим экскурсовода

Киоск в любом режиме (Loop, Browse) поддерживает удалённое управление с планшета экскурсовода через MQTT. Элементы управления экскурсовода НЕ отображаются на самом киоске.

**Возможности экскурсовода:**
- Выбор и запуск медиаконтента на киоске
- Доступ к контенту из «Папки экскурсовода» (скрыт от посетителей)
- Управление воспроизведением: пауза, воспроизведение, перемотка
- Переключение зацикленного воспроизведения
- Управление громкостью
- Выход из режима экскурсовода (возврат киоска к контенту по умолчанию)

### 3.3 Контент только для экскурсовода (Папка экскурсовода)

Контент, помеченный как «только для экскурсовода»:
- **Скрыт** от посетительских дисплеев во всех режимах
- **Доступен** только через управление с планшета экскурсовода
- **Фильтруется** автоматически из плейлистов и меню
- **Хранится** локально вместе с обычным контентом для офлайн-доступа экскурсовода

### 3.4 Таймаут бездействия и авто-сброс

1. ПО отслеживает активность пользователя (касания экрана), в том числе когда видео на паузе
2. По достижении таймаута бездействия появляется предупреждение с обратным отсчётом (например, «Вы ещё здесь?»)
3. Предупреждение содержит кнопку «Остаться» — нажатие сбрасывает предупреждение и таймер
4. Если пользователь не ответил до истечения отсчёта — киоск возвращается в состояние по умолчанию
5. При сбросе: громкость и позиция видео возвращаются к значениям по умолчанию

Таймаут бездействия и длительность обратного отсчёта настраиваются для каждого киоска.

### 3.5 Интеграция с IoT-устройствами

**Физические триггеры (IoT-кнопки):**
- Интеграция через протокол обмена сообщениями Umka (MQTT)
- Получение событий триггеров от IoT-устройств
- Запуск настроенного контента на связанном киоске
- Привязка триггер-киоск и триггер-контент настраивается в CMS

### 3.6 Многоязычность

- Динамическое переключение локали через MQTT-команду
- Локализованная доставка контента из CMS
- Сохранение предпочтения локали для каждого киоска

**Стандартные локали:** `ru` (русский), `en` (английский). Дополнительные локали могут быть добавлены для каждого музея.

## 4. Архитектура Local-First

Киоски Umka следуют архитектуре **local-first**. Киоск всегда работает с локально сохранённым контентом. Подключение к серверу используется для синхронизации, а не для основной работы.

### 4.1 Принцип

```
┌─────────────────────────────────────────────────┐
│                  КИОСК                            │
│                                                   │
│  Локальное хранилище ──→ Движок воспроизведения   │
│       ↑                                           │
│       │ (фоновая синхронизация при наличии сервера)│
│       ↓                                           │
│  Сервис синхронизации ──→ Сервер (CMS)            │
│                                                   │
└─────────────────────────────────────────────────┘
```

- Контент **всегда воспроизводится из локального хранилища**, независимо от подключения к серверу
- Синхронизация работает в фоне и не прерывает воспроизведение
- Отключение сервера не оказывает немедленного влияния на работу киоска
- Новый контент становится доступен только после успешной синхронизации и локального кэширования

### 4.2 Синхронизация

Синхронизация — **по триггеру**, не по опросу. Киоск скачивает контент только по команде.

**Триггер:** CMS публикует MQTT-команду `sync` в `umka/kiosks/{slug}/commands/app`. Это происходит автоматически при сохранении контент-пакета (через `afterChange` хук) или когда администратор нажимает «Синхронизировать» в панели управления.

**Что обращается к серверу:**
1. Метаданные пакета — всегда запрашиваются из REST API CMS (`GET /api/content-packages/{id}?depth=3`). Это небольшой JSON, описывающий все ссылки на медиа. **Всегда серверный запрос.**
2. Медиафайлы — каждый файл проверяется по локальному кэшу:
   - Если файл существует локально (по media ID) И контрольная сумма совпадает → **пропуск (без серверного запроса)**
   - Если файл отсутствует или контрольная сумма отличается → **скачивание с сервера**

**Что остаётся локальным:**
- Воспроизведение всегда читает из локального хранилища (протокол `media-cache://` в Electron)
- Плеер **никогда не стримит с сервера** при обычной работе
- Если сервер упадёт во время воспроизведения — ничего не изменится, контент уже локальный

**Текущее ограничение (TD-001):** Сверка по контрольным суммам запланирована, но ещё не реализована. Сейчас файлы сопоставляются только по media ID. Если файл заменён на сервере (тот же ID, другое содержимое), киоск не обнаружит изменение и будет показывать устаревший контент до очистки кэша. См. `plans/tech-debt.md` TD-001.

**Итого по поведению синхронизации:**
- Фоновое скачивание не прерывает текущее воспроизведение
- Переключение на новый контент после кэширования всех файлов
- Неудачные загрузки пропускаются (остальные файлы синхронизируются); ошибки логируются

### 4.3 Потеря связи

При потере соединения с сервером:

1. Контент продолжает воспроизводиться из локального хранилища (без прерываний)
2. Heartbeat прекращается — сервер помечает киоск как offline
3. Удалённое управление по MQTT недоступно до восстановления соединения
4. Попытки автоматического переподключения продолжаются в фоне
5. При восстановлении: возобновление heartbeat, проверка обновлений контента

**Примечание:** Команды экскурсовода и IoT-триггеры требуют подключения к серверу и недоступны в офлайн-периоды.

## 5. Протокол MQTT

### 5.1 Структура топиков

**Формат:** `umka/kiosks/{kioskSlug}/{category}/{type}`

Где `{kioskSlug}` — уникальный текстовый идентификатор каждого киоска.

**Категории:**
- `commands/*` — Сервер/Экскурсовод → Плеер (управление контентом и воспроизведением)
- `system/*` — Сервер → Сервис (управление питанием и жизненным циклом приложения)
- `status` — Плеер → Сервер (отчёт о состоянии)
- `heartbeat` — Плеер → Сервер (мониторинг состояния приложения)
- `system/heartbeat` — Сервис → Сервер (мониторинг состояния системы)

### 5.2 Системные топики (Сервер → Сервис)

В продуктивных развёртываниях команды управления питанием и жизненным циклом приложения обрабатываются отдельным сервисом управления (control plane), работающим независимо от плеера. Это обеспечивает удалённую управляемость, даже если приложение плеера зависло или упало.

#### Управление питанием
**Топик:** `umka/kiosks/{kioskSlug}/system/power`

| Payload | Описание |
|---------|----------|
| `"on"` | Включение через Wake-on-LAN (magic packet) |
| `"shutdown"` | Выключение ОС |
| `"reboot"` | Перезагрузка ОС |

#### Жизненный цикл приложения
**Топик:** `umka/kiosks/{kioskSlug}/system/app`

| Payload | Описание |
|---------|----------|
| `"start"` | Запуск приложения плеера |
| `"stop"` | Остановка приложения плеера |
| `"restart"` | Остановка и перезапуск приложения плеера |

#### Heartbeat сервиса
**Топик:** `umka/kiosks/{kioskSlug}/system/heartbeat`
**QoS:** 0
**Retain:** true
**Интервал:** Каждые 10 секунд

**Payload:**
```json
{
  "kioskId": "kiosk-1-1",
  "timestamp": "2026-02-08T12:00:00Z",
  "version": "1.0.0",
  "uptime": 3600,
  "player": {
    "status": "running",
    "pid": 1234,
    "lastHeartbeat": "2026-02-08T12:00:00Z",
    "restartCount": 0,
    "lastCrash": "2026-02-08T11:55:00Z",
    "crashedVersion": "1.0.0"
  },
  "system": {
    "cpuPercent": 45,
    "memoryPercent": 62,
    "networkConnected": true
  }
}
```

**Значения статуса плеера:** `running`, `stopped`, `updating`, `unresponsive`, `restarting`

> **Примечание:** Упрощённая MIT-реализация не включает отдельный сервис управления. Команды питания и жизненного цикла обрабатываются внутри самого плеера. Продуктивные развёртывания ДОЛЖНЫ использовать отдельный сервис для надёжности.

### 5.3 Топики команд контента (Сервер/Экскурсовод → Плеер)

#### Синхронизация контента
**Топик:** `umka/kiosks/{kioskSlug}/commands/app`

## 9. Управление питанием и Control Plane (Сервис)

### 9.1 Разделение Control Plane

В продуктивных развёртываниях системное управление (питание, жизненный цикл приложения, watchdog) ДОЛЖНО обрабатываться отдельным сервисом управления (control plane), работающим независимо от плеера. Это обеспечивает удалённую управляемость, даже если плеер не отвечает.

**Обязанности сервиса:**
- Управление питанием ПК (включение через WoL, выключение, перезагрузка)
- Управление жизненным циклом плеера (запуск, остановка, перезапуск)
- Watchdog (автоматическое восстановление плеера при сбое или зависании)
- Отчёт о состоянии системы (CPU, RAM, сеть)

**Обязанности плеера (content plane):**
- Воспроизведение контента и навигация
- Настройки контента (громкость, локаль, зацикливание)
- Синхронизация контента с CMS
- Статус и heartbeat уровня плеера

Сервис наблюдает за плеером через три канала:
1. **Мониторинг процесса ОС** — жив ли процесс плеера?
2. **Подписка на MQTT heartbeat** — отвечает ли плеер?
3. **Lock-файл файловой системы** — идёт ли обновление плеера?

> **Примечание:** Упрощённая MIT-реализация не включает сервис управления. Она обрабатывает команды питания и жизненного цикла внутри самого плеера. Это допустимо для разработки и небольших развёртываний, но не рекомендуется для продуктивного использования.

### 9.2 Wake-on-LAN (Включение)

- BIOS: Wake-on-LAN включён
- Сетевая карта: поддержка WoL включена
- Magic packet: UDP-broadcast на порт 9

### 9.3 Выключение / Перезагрузка

При получении команды питания через топик `system/power` сервис ОБЯЗАН:
1. Опубликовать обновлённый статус (player.status = "stopped")
2. Корректно остановить процесс плеера
3. Выполнить команду выключения/перезагрузки ОС

### 9.4 Watchdog (Автоматическое восстановление)

Сервис реализует трёхуровневое восстановление при обнаружении сбоя или зависания плеера:

1. **Уровень 1 — Корректный перезапуск:** Запуск плеера, ожидание 5 секунд для выхода в рабочий режим
2. **Уровень 2 — Принудительный перезапуск:** Завершение дерева процессов плеера (на Windows: `taskkill /F /T`), повторный запуск, ожидание 30 секунд
3. **Уровень 3 — Размыкатель (circuit breaker):** После `maxRestarts` неудачных перезапусков (по умолчанию: 3) прекращение попыток. Отчёт `player.status = "unresponsive"` в heartbeat

Размыкатель сбрасывается после 30-минутного периода охлаждения (по времени, отсчёт от момента срабатывания размыкателя).

### 9.5 Координация обновления плеера

Плеер использует собственный механизм обновления (например, electron-builder auto-update). Сервис не участвует в обновлениях — он только приостанавливает watchdog на время обновления.

1. Плеер записывает файл `updating.lock` перед началом обновления
2. Сервис обнаруживает lock-файл, приостанавливает watchdog (льготный период: 3 минуты)
3. Плеер завершает обновление, перезапускается, удаляет lock-файл
4. Сервис возобновляет нормальный мониторинг

Если lock-файл сохраняется дольше льготного периода, сервис считает обновление неудачным и приступает к восстановлению Уровня 1.

## 10. Безопасность

**Минимальные требования:**
- MQTT через TLS (порт 8883) для продуктива
- REST API через HTTPS
- Аутентификация киоска по UUID

**Рекомендуется:**
- Клиентские сертификаты MQTT
- Изолированный VLAN для сети киосков
- Аутентификация по API-ключу
- Режим киоска на уровне ОС (предотвращение доступа пользователя к рабочему столу)
- Отключение внешних USB/устройств ввода

## 11. Чек-лист соответствия

Umka-совместимый плеер ОБЯЗАН:

- [ ] Реализовать хотя бы один стандартный режим (Loop, Browse или Custom)
- [ ] Следовать структуре MQTT-топиков и форматам сообщений
- [ ] Публиковать статус при изменении состояния
- [ ] Публиковать heartbeat каждые 10 секунд
- [ ] Работать с локально сохранённым контентом (local-first)
- [ ] Синхронизировать контент через REST API
- [ ] Фильтровать контент экскурсовода из посетительских дисплеев
- [ ] Автоматически переподключать MQTT при потере соединения

**Продуктивные развёртывания ДОЛЖНЫ:**
- [ ] Использовать отдельный сервис управления (control plane) для питания и жизненного цикла
- [ ] Реализовать watchdog с многоуровневым восстановлением
- [ ] Отчитываться о состоянии системы (CPU, RAM) через heartbeat сервиса
- [ ] Поддерживать координацию обновлений через lock-файл

**Рекомендуется:**
- [ ] Поддержка всех трёх режимов работы
- [ ] Поддержка переключения локали
- [ ] Плавные переходы между контентом
- [ ] Таймаут бездействия с авто-сбросом
- [ ] Интеграция с IoT-триггерами
- [ ] Оптимизация жестов для сенсорного ввода

## 12. Что этот стандарт НЕ определяет

Следующее явно оставлено на усмотрение каждой реализации:

- **UI/UX-дизайн** — Визуальный дизайн, анимации и вёрстка индивидуальны для каждого клиента
- **Механизм хранения** — IndexedDB, файловая система, SQLite — на выбор разработчика
- **Поддержка видеокодеков** — Помимо обязательных форматов, реализации могут поддерживать дополнительные кодеки
- **Игровая логика** — Приложения режима Custom определяют собственное поведение
- **Аппаратные функции** — Коррекция трапеции, мультимониторность и т.д.
- **Механизм обновления** — Каким образом обновляется само ПО киоска
- **Реализация сервиса** — Стандарт определяет MQTT-контракт для системного управления; реализация сервиса (язык, упаковка, менеджер сервисов) не предписывается
